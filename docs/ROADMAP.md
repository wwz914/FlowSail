## 0. 一页结论

当前项目缺的不是"更多节点类型"，而是**能让编辑器跑起来的地基**。按投入产出排序，初期应依次完成：

1. **工程地基**（测试、类型、构建、CI）——不先做，后面每加一个交互都在裸奔；
2. **画布交互闭环**（缩放平移、锚点连线、选择删除、撤销重做）——这是"编辑器"与"画布"的分水岭；
3. **节点体系与配置**（类型注册表、6 类基础节点、配置面板、变量引用）——这是"能编排"的前提；
4. **运行与调试**（Runner 接口、试运行、运行记录）——这是"能验证流程正确"的关键；
5. **交付能力**（文档、示例、构建产物、发布）——决定别人能不能用起来。

扣子的 20+ 节点类型、知识库、数据库、发布 API、多人协作**都不在初期范围**，靠注册表与接口外置。

v1.0（2026-11-03 合并，PR #13）已完成第 1 项（工程地基）和第 2 项的一部分（视口、锚点、连线创建与校验）。v1.1（2026-11-03 实施，按 §7）已收口第 2 项——选择、删除、撤销重做与节点创建入口——M1 的"能编"闭环成立。v1.3（2026-11-03 实施，按 §8）已完成第 3 项的前半段：**节点类型注册表 + 6 类内置节点 + 条件分支 + 配置面板**，把"能编"推进到"能配"。v1.4（2026-11-03 实施，按 §9）补齐第 3 项的后半段：**文档模型 + 变量引用 + 文档级校验**，让流程"能存、能传、能引用、能校验"。v1.5（按 §10）完成第 4 项：**Runner 接口、试运行、运行记录、节点运行态**，让流程"能跑"。

## 2. 阶段规划

> 顺序原则：**先地基、后交互、再配置、最后运行**。每一阶段结束都应是一个可演示、可回归的版本。
> 工作量为人日粗估，按单人全职口径，误差 ±50%。

### M1：工程地基 + 可用画布（前置，约 10–14 人日）

#### 2.1 工程地基（必须先做）

| 编号 | 任务 | 为什么初期必须 | 验收标准 |
| --- | --- | --- | --- |
| G-1 | 修 `example` 的 `@system/types.ts` 解析（在 `tsconfig.app.json` 增加 `paths` 或统一导入写法） | 当前 `pnpm --filter example build` 有 8 处 TS 错误，任何类型检查都无从谈起 | `pnpm --filter example build` 的 TS 错误清零 |
| G-2 | 修 `store.setNodes` 类型（声明成 `Node[] \| ((nodes: Node[]) => Node[])`） | 类型与实现不一致，函数式更新无法通过检查 | `tsc` 通过，`NodeRenderer` 不再用 `any` |
| G-3 | 修 `NodeRenderer` 的 Hooks 违规（把节点抽成独立组件，hook 在组件顶层） | 节点数量变化会直接崩溃，后续所有节点交互都建在它上面 | 增删节点不报 "Rendered more hooks"，并有对应测试 |
| G-4 | 引入测试框架（推荐 Vitest + Testing Library）与 `pnpm test` | 仓库当前零测试，交互改动无回归保护 | 至少覆盖 `applyNodeChanges`/`applyEdgeChanges` 与一个节点渲染用例；`pnpm test` 全绿 |
| G-5 | 统一根脚本：`dev`/`build`/`test`/`lint`；修复或替换 rollup 构建 | 根 `package.json` 只有 `test`，且 rollup 因 tsconfig `module: NodeNext` 失败 | 四条命令本地可跑；构建产物能产出 |
| G-6 | CI（GitHub Actions）：install → lint → test → typecheck | 没有 CI 就没有合并门槛，文档与代码容易漂移 | PR 上自动执行，失败阻断合并 |

#### 2.2 画布交互闭环

| 编号 | 任务 | 验收标准 |
| --- | --- | --- |
| C-1 | 视口：缩放（25%–200%，指针锚点）、平移（空格/中键/双指）、比例显示与重置 | 缩放不漂移；比例与真实值一致 |
| C-2 | 适应画布（fit view），空画布禁用 | 一键框住全部节点，含内边距 |
| C-3 | 分层：HTML 节点层 + SVG 连线层 + 交互层；点阵网格背景 | 层序正确，指针事件不互相遮挡 |
| C-4 | 锚点：节点声明输入/输出锚点，悬停高亮，命中区 ≥ 12px | 6 类节点锚点位置正确 |
| C-5 | 连线创建：输出锚点拖到输入锚点，实时预览，非法目标禁用并提示 | 能搭出"开始→大模型→结束"链路 |
| C-6 | 连线渲染：贝塞尔 + 箭头 + hover/选中高亮 | 连线随节点移动实时更新 |
| C-7 | 连线校验：禁自连、禁重复、单入约束 | 非法操作有明确反馈，不产生脏数据 |
| C-8 | 选择：单选、Shift 追加、空白取消、框选（P1） | 选中态与实际选中集合一致 |
| C-9 | 删除：节点连同其连线一起删除，连线单独可删 | 删除后无悬空连线 |
| C-10 | 撤销/重做：历史栈 + 拖拽合并 + 快捷键 | 拖拽、删除、连线、参数修改均可撤销/重做 |
| C-11 | 节点卡片视觉：图标、标题、类型徽标、选中/悬停态 | 与 PRD §6.3 一致 |

**M1 完成定义（DoD）**：G-5 落地后，用根脚本 `pnpm dev` 打开示例，能从空画布拖入节点、连线、删除、撤销到初始态；`pnpm test` 与 CI 全绿；`pnpm build` 通过。

### M2：节点体系与配置（约 10–14 人日）

| 编号 | 任务 | 验收标准 |
| --- | --- | --- |
| N-1 | 节点类型注册表（类型 → 图标/默认数据/锚点/参数 schema/渲染器） | 新增一种节点 ≤ 1 个文件，无需改内核 |
| N-2 | 6 类内置节点：开始、结束、大模型、插件、条件、代码 | 各自有图标、默认数据、锚点、参数 schema |
| N-3 | 条件节点多出口 + 分支标签 | 出口可命名，标签显示在连线上 |
| N-4 | 配置面板：名称、描述、参数表单（string/number/boolean/select/json） | 修改立即反映到文档，重开面板值一致 |

| N-6 | 输入/输出预览（类型 + 描述） | 面板能展示节点入参 schema |
| N-7 | 文档模型：`Workflow` schema、版本号、导出/导入、迁移函数 | 导出的 JSON 可重新导入并完整还原 |

| N-9 | 示例应用升级：左节点面板（拖入画布）+ 三栏布局 | 示例即产品演示，覆盖主要交互 |

**M2 完成定义**：在示例中搭一个带条件分支的流程，改参数、引用上游变量、导出 JSON、重新导入后完全还原，校验面板无错误。

> **M2 的拆分**：M2 不会一个版本做完。v1.3 做 N-1 ~ N-4（注册表、6 类节点、条件多出口与分支标签、参数表单）与 N-6 的一部分；v1.4 做 N-5 / N-6 其余 / N-7 ~ N-9（M2 收口）。见 [§8](#8-v13-范围) 与 [§9](#9-v14-范围)。

## 3. 依赖关系

```
G-1..G-6 工程地基
   ├─▶ C-1..C-3 视口
   │     └─▶ C-4..C-7 锚点 / 连线
   │           └─▶ C-8..C-9 选择 / 删除
   │                 └─▶ C-10 撤销 / 重做
   └─▶ N-1..N-3 节点注册表
         └─▶ N-4..N-6 配置面板
               └─▶ N-7..N-8 文档 / 校验
                     └─▶ R-1..R-6 运行调试
                           └─▶ D-1..D-5 交付
```

要点：

- **G-3（Hooks 修复）必须早于 C-8/C-10**，否则选择与历史栈会踩同一个坑；
- **N-7（文档模型）应早于 R-1**，Runner 直接消费 `Workflow` 文档；
- **D-1（构建）依赖 G-1/G-5**，不要在类型错误未清零时做发布。

## 5. 明确暂不做（防止范围蔓延）

| 能力 | 结论 | 理由 |

| 20+ 节点类型 | 不做 | 用注册表扩展，业务节点交宿主 |

| 移动端 | 不做 | 编辑场景以桌面为主 |

## 7. v1.1 范围（M1 收口）

> 状态：**已确认并实施**（负责人 2026-11-03 确认，实施结果见 §7.9）。
> 目标：让 M1 的完成定义成立，把"能画"变成"能编"。

### 7.1 为什么先收口 M1

M1 的 DoD 要求：用 `pnpm dev` 打开示例后，**能从空画布创建节点、连线、删除、撤销到初始态**。当前差距：

| DoD 要素 | 现状 |
| --- | --- |
| 从空画布创建节点 | ❌ 画布没有任何添加入口，节点只能由宿主 props 传入 |
| 连线 | ✅ 已完成 |
| 删除 | ❌ C-9 未做，画布上无法删除节点或连线 |
| 撤销到初始态 | ❌ C-10 未做 |

如果跳过这一步直接进 M2（节点注册表 + 配置面板），会得到一个"能配置但改坏了撤不回"的编辑器；而且注册表、配置面板本身的交互测试都缺少**选择**与**删除**这两个基础原语，M2 的测试只能直接操纵 store，验证不到真实交互。因此 v1.1 取 M1 收口。

### 7.2 范围

### 8.2 为什么 v1.3 做"节点体系 + 配置面板"

M2 整体（N-1 ~ N-9，10–14 人日）一个版本做不完，需要切一刀。切点按**依赖链**而非按"好做程度"：

```
N-1 注册表 ──▶ N-2 六类节点 ──┬──▶ N-4 参数表单 ──▶ N-5 变量引用 ──▶ N-7 文档模型
     │                        │
     └──▶ N-3 条件分支 ────────┘
```

- **N-1/N-2 是所有后续能力的地基**：注册表定义了"新增一种节点类型要改几个文件"的契约（PRD 成功指标：宿主注册自定义节点改动 ≤ 1 个文件）。不做注册表，N-4 的参数表单与 N-3 的锚点都会硬编码在 `NodeCard` 里，后面必然返工。
- **N-4 是"能配"与"只能看"的分界**：没有参数表单，节点就只是图形，用户配不了 Prompt、设不了条件——整个产品仍然只是"画布"。
- **N-5（变量引用）依赖 N-7 的文档 schema**，且需要上游拓扑推导（FR-P3）。v1.3 若塞进来，文档 schema 会被迫在没定型前先定，反而拖累后续版本。
- **N-3 条件分支**是 M2 里唯一能立刻体现"编排"而不是"画图"的能力（多出口 + 分支标签），且与 N-1 的锚点定义共用同一套契约，顺手做掉成本最低。

因此 v1.3 = **N-1 + N-2 + N-3 + N-4，再加一条"参数修改入历史栈"（R3-7）**，把 N-5 / N-6 / N-7 / N-8 / N-9 整块留给 v1.4。

### 9.1 版本定位与主题

版本序列见 [§8.1](#81-版本定位)：v1.0 → v1.1 → v1.3 → **v1.4**。v1.2 不出现在序列中，仓库不再交待"轮次"。

### 9.2 为什么 v1.4 做"文档模型 + 变量引用 + 校验"

v1.3 之后，M2 剩下的 N-5 / N-6（其余）/ N-7 / N-8 / N-9 是一组**共享同一份契约**的能力：

```
N-7 文档模型 ──┬──▶ N-5 变量引用 ──▶ N-6 输入/输出预览（静态部分）
   │           └──▶ N-8 文档级校验
   └──▶ N-9 工具栏（导出 / 导入）+ 受控 workflow API
```

- **N-7 是轴心**：变量引用要落到文档字段上，校验要按 schema 判"必填缺失"，导入导出要按 schema 校验并迁移版本——三者共用同一份 schema。schema 先定一次，后面不返工。
- **受控 API 与 N-7 绑定**：PRD Q4 已确认"受控 `workflow` + `onChange` 随 N-7 一起定"；宿主要持有文档，前提是文档是完整的一等对象。
- **M3 依赖 N-7**：§3 的依赖链里 N-7（文档模型）必须早于 R-1（Runner）——Runner 直接消费 `Workflow` 文档。v1.4 把文档定下来，M3 才能开跑。
- **与 M3 不冲突**：运行期能力（试运行、运行记录、运行态）依赖 Runner 与运行期数据模型，塞进来只会让 v1.4 的范围失控；v1.4 只做静态契约。

因此 v1.4 = **M2 收口**：做完之后产品从"能编能配"变成"能编能配能存能引用能校验"，M3（能跑）才有地基。

### 10.2 为什么 v1.5 做"运行与调试"

v1.4 之后，M2（M1 ~ M2 已全部收口）与 M4 之间只剩 M3 一个阶段。M3 是 §3 依赖链的下一环：

```
N-7 文档模型（✅ v1.4）──▶ R-1 Runner 接口 ──▶ R-2 试运行 ──▶ R-4 运行记录
                              │                      │
                              └─▶ R-3 节点运行态 ◀────┘
```

- **文档是 Runner 的唯一输入**：§3 明确"N-7 必须早于 R-1，Runner 直接消费 `Workflow` 文档"。v1.4 把文档 schema 定下来（`id` / `name` / `version` / `nodes` / `edges` / `viewport` / `meta`，`CURRENT_WORKFLOW_VERSION = 1`），M3 才具备开工前提。
- **变量引用需要一个运行时来兑现**：`{{nodeId.field}}` 在 v1.4 只做到**静态**层面的解析与标红——能判断引用是否有效，但没有任何东西去**取值**。用户配好一条链路，仍然无法知道"这条流程跑起来会产出什么"。R-1 的 Runner 提供了取值发生的场所，R-2 提供了用户看到结果的入口。
- **"能跑"是产品价值链的最后一环**：编排 → 配置 → 引用 → 校验 → **运行**。缺了运行，前四步产出的仍是一份静态文档，用户无法验证自己的编排是否正确，产品的核心价值链断在最后一环。
- **PRD §5 的设计原则 5 要求"状态可见"**："运行态、错误态、校验态直接呈现在画布上，而不是只藏在日志里"。这条原则今天只兑现了校验态（v1.4 的校验面板）；v1.5 补上运行态与错误态，是把设计原则补齐，而不是新增方向。
- **与 M4 无冲突**：M4 是交付与生态（打包、发布、主题、部署），与运行期能力正交；v1.5 不需要动构建链路与发布流程。

因此 v1.5 = **M3 收口**：做完之后，FlowSail 从"工作流编辑器内核"变成"**可执行的**工作流编辑器内核"。

### 10.5 完成定义（DoD）

在示例应用中：**点击"试运行" → 开始节点进入 `running` → 大模型节点拿到开始节点的实际输出（`{{start.query}}` 被替换成运行期真实值，而非字面量）→ 条件节点按判断结果走"是 / 否"分支，未走到的分支节点标记为 `skipped` → 全部结束后节点分别呈现 `success` → 运行记录面板逐节点列出状态与耗时 → 故意把大模型节点的参数改坏后重跑，失败节点在画布上标红、在记录面板里给出可读错误，点击记录行可定位到该节点 → 修好参数重跑成功**。

工程门槛：`pnpm test` / `typecheck` / `build` / `lint` 与 CI 全绿；新增单测覆盖 Runner 接口契约、Mock Runner 的拓扑执行顺序、运行期变量替换与取值失败、取消行为、运行态与记录的一致性；PR 附同一视口、同一场景（试运行中的画布）的 Before / After 截图。

### 10.6 顺序与依赖

1. **R5-1 Runner 接口**最先做——R5-2 / R5-4 / R5-8 都挂在它上面，先定契约再填内容；
2. **R5-2 Mock Runner**紧随其后（与 R5-3 一起做：Mock Runner 产出假数据，R5-3 用它做变量替换，两者互相验证）；
3. **R5-3 运行期变量解析**在 Mock Runner 就位后做（依赖上游节点已产出输出）；
4. **R5-4 试运行与取消**（依赖 R5-1 ~ R5-3 的完整链路）；
5. **R5-5 节点运行态**（依赖 R5-4 的状态回报时机）；
6. **R5-6 运行记录面板**（与 R5-5 共享同一份运行期数据源，二者必须同时定数据形状，否则会出现"画布显示成功、记录显示失败"的漂移）；
7. **R5-7 错误呈现**（依赖 R5-6 的错误数据结构）；
8. **R5-8 单节点测试**（复用 R5-1 的 Runner 接口与 R5-3 的变量解析）；
9. **R5-9 工具栏与示例**最后做，用来串起整条链路并产出 Before / After 截图；
10. **R5-10 文档同步**收尾。

### 10.8 备选方案

**备选方案 B：只做"Runner 接口 + 试运行 + 节点运行态"**（R5-1 / R5-2 / R5-4 / R5-5 / R5-10，约 6–8 人日）

- **收益**：范围最小、最快出可见效果；画布上能看到节点跑起来、变色。
- **代价**：没有运行记录面板，用户看到红色节点却不知道**为什么**失败、输入输出是什么——"能跑但看不懂"，调试价值只兑现一半；FR-R3 / FR-R4 继续悬空。
- **建议**：除非 v1.5 首要目标只是把"可执行"的对外契约（`Runner` 接口）先稳定下来，否则选 §10.3 的完整范围。

**备选方案 C：把单节点测试（R5-8）推到 v1.6**

- **收益**：R5-8 的交互（面板内手填输入、单独执行）与整条流程的试运行是两条路径，共用 R5-1 / R5-3 却不共用状态管理；推迟可让 v1.5 聚焦"整体试运行"这一条主链路。
- **代价**：FR-P5 继续延后；用户排查"某个节点单独对不对"仍需跑整条流程。
- **建议**：若 R5-1 ~ R5-7 的实现已接近整条链路的预算上限，可切备选方案 C，其余范围照做。

**备选方案 D：整版切到交互增强**（框选 / 复制粘贴 / 节点重命名 / 网格吸附，即 v1.4 与 v1.5 都推迟的 P1 交互项）

- **收益**：编辑器手感提升明显，见效快，对不接执行后端的宿主更友好。
- **代价**：M3 继续推迟，产品的价值链仍停在"能校验但不能跑"；且 M4 的打包与发布准备尚未完成，晚一个版本交付"可执行内核"对外部集成的意义大于交互打磨。
- **建议**：除非当前明确不接执行后端、只做纯编辑器，否则不推荐。

### 10.9 与待确定事项的关系

PRD Q8（试运行中是否禁止编辑）在 v1.4 规划时已归属 M3，此处**收敛为"运行中禁止编辑"**：编辑会让运行态与实际文档脱节，比"允许编辑并重算"简单可靠。

v1.5 需要确认：

| # | 事项 | 建议默认 | 阻塞 v1.5 |
| --- | --- | --- | --- |
| Q18 | §10.3 的范围（完整范围 vs 备选方案 B） | 完整范围（§10.3） | 是 |
| Q19 | `Runner` 接口形态：`run(workflow, hooks, signal)` 单方法，还是把节点执行拆成可独立调用的 `executeNode` | 单方法 `run` 为主，另导出 `executeNode` 供单节点测试复用 | 否（建议默认） |
| Q20 | 运行结果是否写回文档 | **不写回**：运行态与运行记录是**视图态**，不进入 `Workflow` 文档、不进历史栈；需要留存由宿主自行持久化 | 否（建议默认） |
| Q21 | Mock Runner 的产出是否需与节点类型声明的 `outputFields` 类型一致 | 一致：Mock 产出必须落在该类型声明的输出字段上，否则 R5-3 的变量替换会出现类型不匹配 | 否（建议默认） |

> **Q20 的理由**：把运行结果写进文档会与 v1.4 的 schema 契约冲突——`Workflow` 描述的是**流程定义**，不是**执行实例**。若把运行态塞进文档，导入导出、schema 迁移、文档指纹去重（`getDocumentKey`）都要跟着改，而宿主通常有自己的运行记录存储。视图态更符合现有架构（store 里已有 `selected` 这类不入历史的视图态先例）。

> **Q21 的理由**：v1.4 已经让节点类型注册表成为变量作用域的**唯一来源**（Q15）。Mock Runner 若产出注册表未声明的字段，变量替换就会在校验通过（静态）后于运行时失败（动态），两套判定互相打架。让 Mock 遵守 `outputFields` 声明，可让"引用是否合法"在静态与运行时用同一把尺子。

Q5（许可证）、Q6（npm 组织）、Q11（版本与发布机制）仍归属 M4；Q9（扣子能力清单复核）不阻塞 v1.5。

**实现过程中修掉的两个问题**：

1. **失败会沿下游传播**：最初只判断"直接上游是否失败"，导致失败节点的下游也跟着报"取不到值"而标红。改为「上游失败或被跳过则下游标 `skipped`」后，一次失败只会有一个节点标红。
2. **单节点测试取不到上游值**：单节点测试没有上游产出，参数里引用了 `{{start.query}}` 就必然失败。测试面板改为**把引用到的上游字段列出来让用户手填**，单节点测试才能真正可用。
