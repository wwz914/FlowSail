## 0. 一页结论

**已经完成的（M1 ~ M4）**：从一个空仓库做到可安装、可在线试用的画布内核——能画、能连、能配、能存、能校验、能跑，并且有主题、键盘可达、npm 包与发布流程。当前公开版本是 `@flowsail/core@0.2.1` / `@flowsail/react@0.2.1`；`0.2.1` 是视觉补丁序列的第一版，功能范围不变。

**下一阶段（M5 / v1.9）**：主题是**运行可控**——把"能跑一条流程"推进到"失败可处理、执行可定位、结果可解释"：

1. **异常策略**：节点级重试、超时、失败后继续 / 走异常分支；
2. **运行到指定节点**：只执行目标节点的上游，用于调试，不再每次都从头跑到尾；
3. **运行观测**：记录尝试次数、耗时与最终去向，运行面板给出汇总。

**为什么不是自动布局 / 小地图**：这些是规模化编辑体验，P2，且不解决真实流程最先遇到的失败问题；排在 v1.11，等真实宿主的大图反馈再定优先级。

**再往后**：v1.10 做复杂控制流（循环 / 并行 / 子工作流），v1.11 做规模化编辑（自动布局 / 小地图 / 分组），v2.0 做 API 稳定与生态（SSR、持久化适配器、多标签等）。

**需要确认**：§6 的 Q37 ~ Q43；其中 **Q37（v1.9 范围）阻塞开工**，其余可先按建议默认。

## 3. 版本与发布约定

- 仓库以**版本**对齐节奏，不再交待"轮次"；每个版本结束时应是一个可演示、可回归的状态。
- 公开包用 changesets 管理版本：新能力走 minor（如 `0.2.0` → `0.3.0`），修复走 patch；两个包版本保持一致。
- 视觉补丁只改样式、模板结构与示例布局，不改公开 API：走 patch，两个包同步 bump；`0.2.1` ~ `0.2.10` 由对应工单逐版驱动，不改变 v1.9 的功能规划。
- 每个版本合并后由维护者触发 Release 工作流（或明确授权代理执行）；Release 正文取自两个包的 `CHANGELOG.md`，并在版本发布后自动创建 GitHub Release（见 [docs/RELEASING.md](./RELEASING.md)）。
- `1.0.0` 之前，公开 API 仍可能按 minor 调整；文档 schema 的版本（当前 `1`，v1.9 计划升到 `2`）与包的 semver 分开演进，导入时按文档版本迁移。
- `1.0.0` 的前置条件：公开 API 与文档 schema 至少一个 minor 无破坏性变更；SSR、持久化适配器与端到端回归有明确归属（见 [§7](#7-更远阶段v110)）。

## 5. 下一阶段：M5（v1.9）——运行可控

> 状态：**规划中，待确认**（Q37）。范围按"完整"给出；若 Q37 选其他方案，§5.3 与 §5.7 相应缩减。

### 5.1 为什么是现在

M1 ~ M4 已把"编辑 → 保存 → 运行 → 交付"闭环走完，PRD 里的 P0 / P1 能力没有欠账。继续往前有两个方向：

- **编辑体验**：自动布局、小地图、节点分组、连线路由；
- **运行语义**：失败处理、部分执行、运行观测。

当前选择后者，理由是：

1. **真实流程最先卡在失败上**，而不是卡在"图太大不好看"。节点超时、偶发失败、失败后要不要继续，是宿主接真实 Runner 后第一批会遇到的问题。
2. **"运行到此节点"已经欠了一版**：`SelectionToolbar` 的注释明确把它留到 v1.9+（Q35），而 `Runner` 目前只能整条运行。
3. **异常策略要动文档 schema**：越晚引入，迁移与兼容成本越高；在 `1.0.0` 之前定清楚更便宜。
4. **自动布局 / 小地图的优先级依赖真实大图反馈**，仓库内自证的价值有限。

当前代码缺口（开工前证据）：

| 缺口 | 现状 | 位置 |
| --- | --- | --- |
| 异常策略 | `Node` 没有重试 / 超时 / 失败处理字段；Runner 失败即整次失败 | `packages/system/src/types.ts`、`packages/react/src/lib/runner.ts` |
| 运行到节点 | `Runner.run(workflow, hooks, signal, context)` 没有目标节点；工具条注释留到 v1.9+ | `packages/react/src/lib/runner.ts`、`components/SelectionToolbar.tsx` |
| 运行观测 | 记录有状态、耗时、错误，没有尝试次数、最终去向与运行汇总 | `packages/react/src/lib/runStore.ts`、`components/RunPanel.tsx` |
| 文档 schema | `CURRENT_WORKFLOW_VERSION = 1`，没有执行策略字段 | `packages/system/src/document.ts` |

**边界不变**：编辑器仍然只定义文档语义、编辑体验与运行态呈现，不执行工作流；重试、超时与分支调度的真实执行由宿主 Runner 负责，内置 Mock Runner 只用于演示与测试。

### 5.2 目标

v1.9 结束时，应能回答"这次运行为什么失败 / 跑到哪 / 重试了几次"：

1. 节点可以声明重试次数、退避、单次超时与失败处理策略，编辑器能校验并呈现；
2. 失败节点可按策略重试、继续独立分支，或改走异常分支；异常分支是文档里的真实连线，导出后仍然成立；
3. 用户可以只运行到某个选中节点，验证中间结果，而不执行下游；
4. 运行面板能显示每个节点的尝试次数、耗时与最终去向，并给出整次运行的汇总；
5. v1 文档能无损导入并按 v2 保存；v2 文档在旧编辑器里会被明确拒绝，而不是静默读错；
6. 新交互有主题变量、键盘路径与测试覆盖，发布门禁保持全绿。

### 5.3 范围

| 编号 | 任务 | 验收标准 |
| --- | --- | --- |
| R9-1 | 文档 schema v2 与迁移 | `Node` 增加可选执行策略：`retry`（次数 / 退避）、`timeoutMs`、`onError`（`fail` / `continue` / `branch`）；默认值不写进文档。`CURRENT_WORKFLOW_VERSION = 2`；`1 → 2` 不写新字段、读取时按默认值处理，保留未知字段，拒绝高于 `2` 的版本。校验覆盖取值范围与"启用异常分支但没连异常线"。v1 文档导入、导出、再导入无损；迁移与校验有测试 |
| R9-2 | 异常策略的编辑与呈现 | 配置面板增加「执行策略」区块（重试次数 / 退避毫秒 / 超时 / 失败处理），只写非默认值；`onError = 'branch'` 时节点出现专用 `error` 出口，连线标签默认「异常」，其余出口行为不变。异常出口可键盘到达、样式走 `--flow-*`，并有 Before / After 截图 |
| R9-3 | Runner 契约与 Mock 执行语义 | 新增 `onNodeRetry` 钩子与尝试次数字段；Mock Runner 实现重试 + 退避、单次超时、三种失败处理：`fail` 整次失败、`continue` 只跳过依赖失败节点的下游、`branch` 走异常出口并跳过正常出口（缺少异常出口时按 `fail` 处理并报错）。运行结果区分"失败且终止"与"失败但已走完"；超时与重试用假定时器测试，不引入不稳定等待 |
| R9-4 | 运行到指定节点 | Runner 契约支持可选的部分执行（形式见 Q40）；控制器提供 `runToNode`，只调度目标节点及其上游子图，条件分支仍按正常语义只走命中的一侧；目标节点之后的节点保持未执行、不产生运行记录。选中单个节点时工具条出现「运行到此」，运行中禁用；Runner 不支持部分执行时给出可读提示并拒绝发起，不静默跑完整条流程。取消、运行锁与现有快捷键语义不变 |
| R9-5 | 运行观测与汇总 | 节点记录增加尝试次数、开始 / 结束时间、最终去向（成功 / 重试后成功 / 失败 / 跳过 / 未执行）；运行面板增加汇总（总耗时、最慢节点、重试次数、失败 / 跳过数），并可按耗时排序。只呈现真实采集到的数据，不展示 CPU / 内存等无法可靠获取的指标 |
| R9-6 | 示例、文档、门禁与发布 | example 增加一条"偶发失败 → 重试 → 仍失败 → 异常分支"的流程与「运行到此」演示；README / PRD / AGENTS / RELEASING 与实现一致；新增 minor changeset，发布 `0.3.0` 并生成 GitHub Release；`pnpm test` / `test:coverage` / `typecheck` / `build` / `lint` / `check:size` / `check:pack` / `check:links` 全绿，体积仍 < 60KB |

### 5.5 完成定义（DoD）

在仓库内与干净环境中：

- **文档**：一份 v1 文档导入后能编辑执行策略，导出为 v2，再导入内容一致；未知顶层字段与 `meta` 字段不丢；大于 `2` 的版本文档给出可读拒绝原因。
- **异常策略**：示例流程中，节点第一次失败、第二次成功；另一个节点重试耗尽后走异常分支；第三个节点失败但独立分支继续执行。三种情况在画布与运行记录里状态一致。
- **运行到节点**：选中一个中间节点执行后，只有其上游与自身有运行记录，下游保持未执行；取消运行能立刻解除运行锁；不支持的 Runner 会明确拒绝并提示，不执行其他节点。
- **观测**：运行面板的尝试次数、耗时、失败 / 跳过数与 Mock 的实际行为一致；汇总数字可复算，不出现伪造指标。
- **工程门槛**：`pnpm test` / `pnpm test:coverage` / `pnpm typecheck` / `pnpm build` / `pnpm lint` / `pnpm check:size` / `pnpm check:pack` / `pnpm check:links` 与 CI 全绿；覆盖率 ≥ 70%，`@flowsail/react` gzip 仍 < 60KB。
- **UI 证据**：执行策略表单、异常出口、运行汇总与「运行到此」按钮提供同一视口、同一场景、同一主题的 Before / After 截图；新增键盘路径有走查记录。
- **发布**：`0.3.0` 的 changeset、CHANGELOG、GitHub Release 可追溯。

### 5.6 顺序与依赖

1. **Q37（范围）先确认**；Q38 / Q40 影响 schema 与公开 API，最迟在开工前定。
2. **R9-1 schema 先行**：执行策略字段、迁移与校验是 R9-2 / R9-3 的地基。
3. **R9-3 Runner 语义**随后；R9-4 只依赖 Runner 契约，可与 R9-3 并行。
4. **R9-2 编辑与呈现**在 R9-1 + R9-3 之后，确保表单与钩子形状一致。
5. **R9-5 观测**在 R9-3 / R9-4 之后，汇总的是最终行为。
6. **R9-6 文档、示例与发布**收尾，检查最终产物。

| R9-2 编辑与呈现 | 3–4 |

### 5.8 备选方案

**方案 B：只做异常策略 + 运行观测**（R9-1 / R9-2 / R9-3 / R9-5 / R9-6，约 12–17 人日）

- **收益**：先解决失败处理与可解释性，schema 与 Runner 改动更小；
- **代价**："运行到此节点"继续欠账（Q35 已经把它推到 v1.9+）；
- **建议**：可作为缩小版；若 Q37 选 B，则在 v1.10 与复杂控制流一起补。

**方案 C：只做规模化编辑（自动布局 / 小地图 / 分组）**（约 8–12 人日）

- **收益**：视觉变化最直观，大图体验提升；
- **代价**：失败处理与部分执行继续缺失，宿主接真实 Runner 后仍会先撞上这些问题；
- **建议**：不推荐；这些能力排在 v1.11。

**方案 D：直接做循环 / 并行 / 子工作流**（约 15–20 人日）

- **收益**：补齐与扣子最大的能力差距；
- **代价**：需要嵌套子图 / 容器节点与执行契约 v3，schema 与 UI 改动都更大；异常策略仍未落地，循环体里的失败处理会继续缺位；
- **建议**：不推荐抢在 v1.9；先做异常策略，再进 v1.10。

**推荐**：方案 A（§5.3 的完整范围），用异常策略、运行到节点与观测把"运行可控"一次做完整。

### 5.9 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| Runner 契约变化影响已接入的宿主 | 宿主自定义 Runner 可能不认新钩子 | 新钩子 / 字段全部可选；部分执行走可选方法，不支持时明确拒绝；minor 版本 + README 迁移说明 |
| `continue` 语义含糊 | 画布、记录与宿主实现各说各话 | 在 Q39 定死"独立分支继续、依赖下游跳过"，用矩阵测试覆盖 |
| 异常出口让节点 UI 变复杂 | 卡片拥挤、键盘路径变长 | 只在 `onError = 'branch'` 时出现；复用现有锚点样式与焦点环；截图对比 |
| 文档 v2 被旧编辑器误读 | 数据错乱 | 旧编辑器明确拒绝更高版本；新编辑器自动迁移 v1；往返测试 |
| 超时 / 退避测试不稳定 | CI 抖动 | Mock 用假定时器；真实 Runner 的超时由宿主负责，编辑器只传 signal 与配置 |
| 范围滑向循环 / 并行 | 版本失控 | §5.4 明确排除；循环相关需求记入 v1.10 |

## 7. 更远阶段（v1.10+）

### v1.10：复杂控制流

- **目标**：让文档能表达循环、批处理、并行与子工作流，并让 Runner 契约能承载它们。
- **关键工作**：容器节点 / 嵌套子图与文档 schema v3；循环的起止、最大轮次与退出条件；并行的汇合语义；子工作流的输入输出映射；画布的展开 / 收起与校验递归。
- **为什么排在 v1.9 之后**：异常策略是循环体的前置——循环里的单轮失败要有明确处理方式；schema v2 先落地，v3 才有稳定的迁移起点。
- **完成定义**：示例能搭出"遍历列表 → 并行处理 → 汇总"的流程，Mock Runner 能跑通，导出 / 导入 / 校验完整。

### v1.11：规模化编辑

- **目标**：大图可读、可整理，补齐与扣子编辑器体验层的差距。
- **候选**：基于拓扑的自动布局（纵向 / 横向）、小地图、节点分组 / 注释、连线路径编辑。
- **触发条件**：真实宿主反馈图规模超过约 100 个节点，或性能基准显示拖拽 / 缩放已需要辅助导航；不在仓库内自证优先级。
- **为什么排在控制流之后**：自动布局要理解容器与循环边界，先有 v1.10 的文档语义再排版更稳。

### v2.0：稳定与生态（公开包 `1.0.0`）

- **目标**：把"可用"变成"可长期依赖"。
- **候选**：公开 API 审计与冻结、SSR 安全、持久化适配器（localStorage / 远程保存）、多标签、自定义配置面板插槽、国际化、端到端回归与文档站。
- **前置条件**：文档 schema 与公开 API 至少一个 minor 无破坏性变更；v1.9 / v1.10 的运行契约经真实宿主验证。
- **非目标**：执行平台、插件市场、多人协作仍不在内核范围内。

## 8. 术语表

| 术语 | 说明 |
| --- | --- |
| 工作流（Workflow） | 一份由节点和连线组成的可执行流程文档 |
| 节点（Node） | 工作流中的一个处理单元，有类型、位置、参数与可选的执行策略 |
| 锚点（Handle） | 节点上用于连接连线的输入 / 输出端口；异常分支使用专用 `error` 出口 |
| 连线（Edge） | 连接两个锚点的有向关系，可有分支标签 |
| 变量引用 | 形如 `{{nodeId.field}}` 的表达式，运行时解析为上游输出 |
| Runner | 执行工作流的接口实现，由宿主注入或使用内置 Mock |
| 运行到节点 | 只执行目标节点及其上游的部分执行模式，用于调试 |
| 异常策略 | 节点级重试、超时与失败处理（终止 / 继续 / 异常分支） |
| 画布（Canvas） | 可缩放平移的二维编辑平面 |
