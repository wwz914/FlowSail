# FlowSail 初期路线图（ROADMAP）

> 配套文档：[产品 PRD](./PRD.md) · [README](../README.md) · [AGENTS.md](../AGENTS.md)
> 适用基线：`main` @ `5724165`（2026-11-03）
> 本文回答一个问题：**对标扣子工作流编辑器，初期到底该先建哪些基础能力、按什么顺序。**

---

## 0. 一页结论

当前项目缺的不是"更多节点类型"，而是**能让编辑器跑起来的地基**。按投入产出排序，初期应依次完成：

1. **工程地基**（测试、类型、构建、CI）——不先做，后面每加一个交互都在裸奔；
2. **画布交互闭环**（缩放平移、锚点连线、选择删除、撤销重做）——这是"编辑器"与"画布"的分水岭；
3. **节点体系与配置**（类型注册表、6 类基础节点、配置面板、变量引用）——这是"能编排"的前提；
4. **运行与调试**（Runner 接口、试运行、运行记录）——这是"能验证流程正确"的关键；
5. **交付能力**（文档、示例、构建产物、发布）——决定别人能不能用起来。

扣子的 20+ 节点类型、知识库、数据库、发布 API、多人协作**都不在初期范围**，靠注册表与接口外置。

---

## 1. 现状盘点

| 能力域 | 现状 | 缺口 | 初期优先级 |
| --- | --- | --- | --- |
| 数据层 | `Node`/`Edge` 类型 + 两个按 id 浅合并的纯函数 | 变更类型不全、无文档 schema、无校验/迁移 | P0 |
| 画布渲染 | 绝对定位 div + SVG 直线 | 无分层规范、无曲线/箭头、无锚点 | P0 |
| 视口 | 无 | 缩放、平移、适应画布、比例显示 | P0 |
| 节点交互 | d3-drag 拖动（Hooks 违规） | 选择、多选、删除、复制、吸附 | P0 |
| 连线交互 | 仅渲染，数据写死 | 创建、校验、删除、标签 | P0 |
| 节点体系 | 无类型概念（`Node.type` 未使用） | 注册表、内置节点、图标、端口定义 | P0 |
| 配置面板 | 无 | 参数表单、变量引用、输入输出预览 | P0 |
| 撤销重做 | 无 | 历史栈、拖拽合并 | P0 |
| 运行调试 | 无 | Runner 接口、试运行、日志、状态 | P1 |
| 文档序列化 | 无 | 导出/导入、版本迁移 | P1 |
| 工程地基 | 无测试、tsc 失败、无构建脚本、无 CI | 测试框架、类型修复、构建、CI | **P0（前置）** |
| 主题/可访问性 | 无 | CSS 变量、键盘可达 | P1/P2 |

**一句话**：除了"能渲染、能拖动"，编辑器该有的能力基本都缺；而工程地基的缺失会让补齐过程反复踩坑。

---

## 2. 阶段规划

> 顺序原则：**先地基、后交互、再配置、最后运行**。每一阶段结束都应是一个可演示、可回归的版本。
> 工作量为人日粗估，按单人全职口径，误差 ±50%。

### M1：工程地基 + 可用画布（前置，约 10–14 人日）

#### 2.1 工程地基（必须先做）

| 编号 | 任务 | 为什么初期必须 | 验收标准 |
| --- | --- | --- | --- |
| G-1 | 修 `example` 的 `@system/types.ts` 解析（在 `tsconfig.app.json` 增加 `paths` 或统一导入写法） | 当前 `pnpm --filter example build` 有 8 处 TS 错误，任何类型检查都无从谈起 | `pnpm --filter example build` 的 TS 错误清零 |
| G-2 | 修 `store.setNodes` 类型（声明成 `Node[] \| ((nodes: Node[]) => Node[])`） | 类型与实现不一致，函数式更新无法通过检查 | `tsc` 通过，`NodeRenderer` 不再用 `any` |
| G-3 | 修 `NodeRenderer` 的 Hooks 违规（把节点抽成独立组件，hook 在组件顶层） | 节点数量变化会直接崩溃，后续所有节点交互都建在它上面 | 增删节点不报 "Rendered more hooks"，并有对应测试 |
| G-4 | 引入测试框架（推荐 Vitest + Testing Library）与 `pnpm test` | 仓库当前零测试，交互改动无回归保护 | 至少覆盖 `applyNodeChanges`/`applyEdgeChanges` 与一个节点渲染用例；`pnpm test` 全绿 |
| G-5 | 统一根脚本：`dev`/`build`/`test`/`lint`；修复或替换 rollup 构建 | 根 `package.json` 只有 `test`，且 rollup 因 tsconfig `module: NodeNext` 失败 | 四条命令本地可跑；构建产物能产出 |
| G-6 | CI（GitHub Actions）：install → lint → test → typecheck | 没有 CI 就没有合并门槛，文档与代码容易漂移 | PR 上自动执行，失败阻断合并 |

#### 2.2 画布交互闭环

| 编号 | 任务 | 验收标准 |
| --- | --- | --- |
| C-1 | 视口：缩放（25%–200%，指针锚点）、平移（空格/中键/双指）、比例显示与重置 | 缩放不漂移；比例与真实值一致 |
| C-2 | 适应画布（fit view），空画布禁用 | 一键框住全部节点，含内边距 |
| C-3 | 分层：HTML 节点层 + SVG 连线层 + 交互层；点阵网格背景 | 层序正确，指针事件不互相遮挡 |
| C-4 | 锚点：节点声明输入/输出锚点，悬停高亮，命中区 ≥ 12px | 6 类节点锚点位置正确 |
| C-5 | 连线创建：输出锚点拖到输入锚点，实时预览，非法目标禁用并提示 | 能搭出"开始→大模型→结束"链路 |
| C-6 | 连线渲染：贝塞尔 + 箭头 + hover/选中高亮 | 连线随节点移动实时更新 |
| C-7 | 连线校验：禁自连、禁重复、单入约束 | 非法操作有明确反馈，不产生脏数据 |
| C-8 | 选择：单选、Shift 追加、空白取消、框选（P1） | 选中态与实际选中集合一致 |
| C-9 | 删除：节点连同其连线一起删除，连线单独可删 | 删除后无悬空连线 |
| C-10 | 撤销/重做：历史栈 + 拖拽合并 + 快捷键 | 拖拽、删除、连线、参数修改均可撤销/重做 |
| C-11 | 节点卡片视觉：图标、标题、类型徽标、选中/悬停态 | 与 PRD §6.3 一致 |

**M1 完成定义（DoD）**：G-5 落地后，用根脚本 `pnpm dev` 打开示例，能从空画布拖入节点、连线、删除、撤销到初始态；`pnpm test` 与 CI 全绿；`pnpm build` 通过。

### M2：节点体系与配置（约 10–14 人日）

| 编号 | 任务 | 验收标准 |
| --- | --- | --- |
| N-1 | 节点类型注册表（类型 → 图标/默认数据/锚点/参数 schema/渲染器） | 新增一种节点 ≤ 1 个文件，无需改内核 |
| N-2 | 6 类内置节点：开始、结束、大模型、插件、条件、代码 | 各自有图标、默认数据、锚点、参数 schema |
| N-3 | 条件节点多出口 + 分支标签 | 出口可命名，标签显示在连线上 |
| N-4 | 配置面板：名称、描述、参数表单（string/number/boolean/select/json） | 修改立即反映到文档，重开面板值一致 |
| N-5 | 变量引用：`{{nodeId.field}}`，选择器按拓扑过滤上游 | 非法引用标红并阻止保存/运行 |
| N-6 | 输入/输出预览（类型 + 描述） | 面板能展示节点入参 schema |
| N-7 | 文档模型：`Workflow` schema、版本号、导出/导入、迁移函数 | 导出的 JSON 可重新导入并完整还原 |
| N-8 | 文档级校验：孤立节点、悬空连线、必填缺失、引用失效 | 生成问题列表，点击可定位节点 |
| N-9 | 示例应用升级：左节点面板（拖入画布）+ 三栏布局 | 示例即产品演示，覆盖主要交互 |

**M2 完成定义**：在示例中搭一个带条件分支的流程，改参数、引用上游变量、导出 JSON、重新导入后完全还原，校验面板无错误。

### M3：运行与调试（约 6–9 人日）

| 编号 | 任务 | 验收标准 |
| --- | --- | --- |
| R-1 | `Runner` 接口：`run(workflow, hooks, signal)`；内置 Mock Runner | 宿主可注入自定义 Runner，接口有类型 |
| R-2 | 试运行：按钮触发、进度、取消、运行中编辑策略 | 能从开始节点跑到结束节点 |
| R-3 | 节点运行态：idle/running/success/error/skipped | 画布颜色与日志状态一致 |
| R-4 | 运行记录面板：节点、状态、耗时、输入/输出，可复制、可定位 | 失败节点能一步定位 |
| R-5 | 单节点测试（右侧面板"测试"按钮） | 手填输入即可执行当前节点并看输出 |
| R-6 | 错误呈现：错误码、消息、堆栈折叠 | 错误不吞、不刷屏 |

**M3 完成定义**：示例流程试运行成功；人为改坏一个参数后失败节点在画布与日志中同时高亮，错误信息可读。

### M4：交付与生态（约 5–8 人日）

| 编号 | 任务 | 验收标准 |
| --- | --- | --- |
| D-1 | 包构建：产出 ESM + `.d.ts`，`exports` 字段正确 | `pnpm build` 产物可被外部工程安装使用 |
| D-2 | 文档：README、PRD、ROADMAP、API 快速上手 | 新用户 10 分钟跑通示例 |

| D-5 | 可访问性与主题（CSS 变量、亮/暗） | 键盘可完成基本编辑，主题可覆盖 |

**M4 完成定义**：外部项目能 `pnpm add` 后嵌入一个可编辑的画布，README 的每个命令都实测可用。

## 3. 依赖关系

```
G-1..G-6 工程地基
   ├─▶ C-1..C-3 视口
   │     └─▶ C-4..C-7 锚点 / 连线
   │           └─▶ C-8..C-9 选择 / 删除
   │                 └─▶ C-10 撤销 / 重做
   └─▶ N-1..N-3 节点注册表
         └─▶ N-4..N-6 配置面板
               └─▶ N-7..N-8 文档 / 校验
                     └─▶ R-1..R-6 运行调试
                           └─▶ D-1..D-5 交付
```

要点：

- **G-3（Hooks 修复）必须早于 C-8/C-10**，否则选择与历史栈会踩同一个坑；
- **N-7（文档模型）应早于 R-1**，Runner 直接消费 `Workflow` 文档；
- **D-1（构建）依赖 G-1/G-5**，不要在类型错误未清零时做发布。

## 5. 明确暂不做（防止范围蔓延）

| 能力 | 结论 | 理由 |
| --- | --- | --- |
| 20+ 节点类型 | 不做 | 用注册表扩展，业务节点交宿主 |
| 知识库 / 数据库 / 多媒体节点 | 不做 | 依赖后端与资源体系 |
| 插件市场 / 插件运行时 | 不做 | 生态能力，非编辑器内核职责 |
| 多人协作 / 评论 / 权限 | 不做 | 协同基础设施成本高 |
| AI 生成工作流 | 不做 | 依赖模型与提示词工程 |
| 发布为 API / Bot | 不做 | 由宿主基于 `onExport` 实现 |
| 移动端 | 不做 | 编辑场景以桌面为主 |

---

## 6. 下一步（可直接开工的三件事）

1. **G-4 + G-3**：先补测试框架与 Hooks 修复，给后续所有交互上保险；
2. **G-1 + G-2 + G-5**：让 `pnpm build`、`pnpm test`、`pnpm lint` 三条命令真正可用；
3. **C-1 + C-4 + C-5**：做出"能缩放、能连线"的最小可用画布，作为第一个可演示版本。

完成这三件事后，再按 M2 推进配置与变量。每一步的验收标准见上文，PR 里按阶段小步提交，避免一次改动跨多个阶段。
